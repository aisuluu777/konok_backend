# Бизнес-правила «Конок»

Номер правила (R-xx) указывай в docstring теста, который его проверяет.
Схема БД: docs/schema.sql.

## Роли и доступ
- R-01. `users.role`: `user`, `moderator`, `admin`. Бронировать (проживание и машину) может `user`
  с одобренным KYC (`users.kyc_status = 'approved'`).
- R-02. Хозяин — `user`, у которого есть `host_profiles`. Владелец машины — `user`, добавивший машину.
  Один пользователь может быть и хозяином, и владельцем машины, и туристом.
- R-03. Хозяин виден в каталоге и принимает брони только при `users.kyc_status = 'approved'`
  и `host_profiles.is_published = true`. Машина видна в каталоге только при `kyc_status = 'approved'`
  владельца и `vehicles.is_published = true`. Заблокированный пользователь (`users.status = 'blocked'`)
  скрыт из каталогов и публичных профилей.
- R-04. Документы KYC видят только их владелец и `moderator` / `admin`. В публичных ответах их нет.
- R-05. Нельзя бронировать проживание у самого себя и арендовать свою машину.

## Профиль хозяина
- R-06. Публично видны регион и населённый пункт. Точный адрес — только гостю, у которого бронь
  этого хозяина в статусе `confirmed`, `in_progress` или `completed`.
- R-07. Видео-визитка необязательна: MP4, не длиннее 120 секунд.
- R-29. Профиль хозяина создаётся одним запросом, когда анкета заполнена целиком:
  регион, населённый пункт, адрес, вместимость, цена. Черновиков на сервере нет —
  если хозяин бросил анкету, при возвращении он заполняет её заново.

## Занятия
- R-08. Хозяин сам создаёт занятия: название, описание, цена за человека больше 0.
  Количество занятий не ограничено. Бесплатных занятий нет.
- R-09. Теги ведёт администратор, хозяин выбирает теги для своего занятия.
  Фильтр каталога «по занятиям» — это фильтр по тегам активных занятий.
- R-10. Купленное занятие не удаляется физически, а скрывается (`is_active = false`).
  В покупке хранится снимок названия и цены.
- R-11. Занятие не привязано к дню визита. Покупается вместе с бронью или докупается, пока бронь
  `confirmed` или `in_progress`. Отдельно не отменяется. Количество людей не больше гостей брони.

## Машины
- R-40. Владелец сам включает и снимает публикацию машины (`is_published`, по умолчанию `true`).
  Машина не удаляется — только снимается с публикации.

## Доступность
- R-12. Свободные места на ночь = `capacity` − сумма `guests_count` броней `stay` в статусах
  `hold`, `confirmed`, `in_progress`, где ночь попадает в `[start_date, end_date)`.
- R-13. Ночь из `blocked_dates` недоступна для новых броней.
- R-14. Хозяин блокирует только целый день и только если на него нет активных броней.
  Прошедшие даты из `blocked_dates` удаляются при записи.
- R-15. Нельзя уменьшить `capacity` ниже уже забронированного на любую будущую ночь.
- R-16. Бронь, блокировка дня и смена вместимости выполняются в транзакции с
  `SELECT ... FOR UPDATE` строки `host_profiles`. Две параллельные брони на последнее место —
  проходит ровно одна.

## Бронирование
- R-17. Типы брони: `stay` (проживание) и `vehicle` (машина). Цена проживания — за человека за ночь,
  машины — за день. Цена копируется в бронь; её изменение не влияет на созданные брони.
- R-18. У туриста не может быть пересекающихся активных броней `stay` (у любых хозяев).
  Дата выезда не входит в период: «выезд 5-го / заезд 5-го» допустимо.
  Аренда машины может пересекаться с проживанием.
- R-19. Одну машину нельзя забронировать на пересекающиеся дни.
- R-20. `hold` удерживает места `settings.hold_minutes` минут; просроченный `hold` становится `expired`.
- R-21. Заезд с 13:00, выезд до 11:00 — одинаково для всех (`settings`). Время прибытия не раньше 13:00.
- R-22. Хозяин не может отклонить или отменить бронь. Он может только обратиться в поддержку.
- R-23. PIN заселения — один на пользователя, 6 цифр. Выдаётся автоматически при одобрении KYC,
  хранится в `users.checkin_pin` и всегда виден владельцу в личном кабинете; владелец может
  перевыпустить PIN (старый перестаёт действовать). Хозяин при заселении (владелец машины при передаче)
  вводит PIN гостя — бронь становится `in_progress`.
  (Решение MVP, не окончательное: PIN хранится открыто.)
- R-24. Гость не приехал и не отменил — бронь `no_show`.

## Чат
- R-25. Один диалог на пару «гость — хозяин или владелец машины»; доступен до брони.
  Оригинал сообщения хранится всегда.

## Отзывы
- R-26. Отзыв можно оставить после завершения брони (`completed`); один отзыв на бронь от автора.

## Поддержка и журнал
- R-27. Жалоба — обращение в поддержку с `category = 'complaint'` и свободным текстом.
  Хозяин жалуется на туриста так же.
- R-28. В `audit_logs` пишутся: решения по KYC, отмены броней, блокировки пользователей,
  изменения настроек.

## Финансы — имитация (пока нет платёжного партнёра)
- R-30. Платежи, выплаты и возвраты имитируются. Реальных денег и внешних API нет.
  Провайдер платежей скрыт за интерфейсом `PaymentProvider`; сейчас единственная реализация —
  `MockPaymentProvider` (`payments.provider = 'mock'`). Подмена на реального партнёра позже
  не должна менять сервисы бронирования.
- R-31. Имитация оплаты: эндпоинт оплаты брони вызывает mock-провайдера, который всегда успешен.
  Для тестов провайдер можно настроить на отказ. Успех: платёж `succeeded`, бронь `hold` → `confirmed`. Отказ: платёж `failed`, бронь остаётся `hold` до истечения срока (R-20).
- R-32. Таблицы `payments`, `payouts`, `refunds`, `booking_activities` работают по схеме как настоящие.
  `idempotency_key` обязателен: повторный запрос оплаты с тем же ключом не создаёт второй платёж.
- R-33. Комиссия: `commission_rate` копируется из `settings` в бронь при создании и действует для всех
  платежей этой брони (включая докупку занятий). `commission_amount = round(amount × commission_rate, 2)`.
  Значение в `settings` сейчас тестовое, а не решение продукта.
- R-34. Отмена туристом в текущем этапе — полный возврат всех успешных платежей брони.
  Mock-возврат всегда успешен. Срок бесплатной отмены и частичный возврат не реализуются.
- R-35. Имитация выплаты: при вводе PIN создаётся `payouts` по всем платежам брони без `payout_id`,
  mock-провайдер сразу помечает выплату `paid`. Докупленное после заселения занятие даёт
  отдельную выплату сразу после оплаты. Неявка (R-24) тоже создаёт выплату хозяину.
  Для аренды машины выплата владельцу создаётся при переводе брони в `completed` — по всем
  успешным платежам без `payout_id`, той же логикой; иначе владелец машины не получит оплату.
- R-36. Валюта везде KGS, конвертации нет.

## Каталог мест, избранное и уведомления
- R-37. Места (`places`) — справочный контент, которым управляет только `admin`:
  создание, редактирование, удаление. Чтение публичное (без авторизации).
  Место привязано к одному региону.
- R-38. Избранное (`favorites`): `user` управляет только своим избранным — добавить и удалить.
  Одна запись указывает ровно на один объект — хозяина, место или машину (`num_nonnulls = 1`).
  Повторно добавить тот же объект нельзя (уникальность на пользователя и цель).
  Пользователь видит и меняет только своё избранное.
- R-39. Уведомления (`notifications`): `user` читает только свои in-app уведомления через `GET`.
  Канал в MVP — только `in_app` (email/sms вне этапа). Уведомление создаётся в одной транзакции
  с событием, для следующих событий:
    – подтверждение брони / успешная оплата — гостю и хозяину (хозяину «новая бронь»);
      докупка занятий (`activities_paid`) — гостю и хозяину;
    – заселение (`in_progress`) — гостю;
    – возврат при отмене — гостю;
    – получен отзыв — пользователю, которого оценили;
    – решение по KYC (`approved` / `rejected`) — пользователю; при `approved` выдаётся PIN (R-23),
      отдельного уведомления о PIN нет, самого PIN в payload нет;
    – `no_show` — гостю и хозяину;
    – выплата проведена (`paid`) — хозяину или владельцу машины.
  Отметка о прочтении — только явная: `POST /notifications/{id}/read` и
  `POST /notifications/read-all`; `GET` не меняет `read_at`.
